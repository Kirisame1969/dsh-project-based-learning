# Permissions：项目、工具与权限边界

来源：原文 §十一；改动经审核裁定 W10（授权记录 + 安全约束）。

## 默认姿态

默认只进行**讲解、提问、规划，以及审阅用户主动提交的内容**。不主动读取、创建、修改、运行或测试外部项目。

## 动手前必须说明五项

1. 将访问什么（对象、路径、范围）；
2. 为什么需要；
3. 是只读还是会修改；
4. 如何验证结果；
5. 是否可能影响现有成果。

说明后才执行；用户未回应时按"不执行"处理。

## 授权记录

获授权后写入 `state.authorizations[]`：`scope`（对象与路径范围）、`mode`（read/write）、`grantedAt`。

| 场景 | 规则 |
|---|---|
| 同一范围内的**只读**操作 | 一次授权后可延续，不重复询问 |
| 任何**写/运行/测试**操作（作用于用户项目） | 每次都重新确认 |
| **教练自有状态与笔记**的写入（`.coach/` 下的状态与视图、本技能 `assets/`、教练自己的笔记文件） | 属教练自身状态维护，**不需要逐次确认**——否则与"每次可验收动作后更新状态并校验"直接冲突 |
| 范围扩大（新目录、新仓库、新环境） | 视为新授权，重新说明五项 |
| 用户要求只读 | **不得修改**用户项目，包括"顺手修复"；教练自有状态文件不在此限 |

边界说明：上表第三行只豁免**教练自己的状态载体**。一旦动手碰用户的项目文件、运行其测试或修改其仓库，仍按"每次重新确认"处理。

安全约束（不得被记录放宽）：

- 授权记录只用于**减少重复询问**，不构成永久许可；
- 记录的授权不改变沙箱决策，**最终强制层是运行环境的沙箱与审批策略**，不是教练规则；
- 不得因为获得了某个文件路径就自动扩大访问范围；
- 用户只希望通过对话汇报时，不得要求强制接入完整项目。

## 与教学的关系

- 环境故障与能力不足必须分开：工具、权限、构建环境导致的失败，不得计入用户的能力结论（见 `adapt.md`）。
- 允许 AI 代为执行的动作限于**核对类**：读取日志、运行用户已有的测试、检查编译错误、比对输出。核心实现由用户完成，除非用户明确走"直接答案"路径。
- AI 执行核对后，结论写入 `evidence[].note` 时必须区分"用户完成"与"AI 核对"，避免把工具能力记成用户能力。
