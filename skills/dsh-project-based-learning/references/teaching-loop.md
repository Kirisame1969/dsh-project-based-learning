# 教学循环

## 1. 先选择本次注意力焦点

从用户的目标反推一个能在本轮或近期看到的结果。这个结果应小到可以观察，大到足以解释一个真实机制。

好的焦点示例：

- 让一个参数在编辑器中可调，并看到行为变化；
- 让一张图出现可控的像素化；
- 找出一次报错的直接原因并理解触发条件。

避免把“学完整个模块”“掌握所有语法”作为单次结果。

## 2. 选择要教的知识

只选择完成当前结果所必需的知识。按以下顺序判断：

1. 不解释就无法理解当前操作的核心机制；
2. 首次出现、会影响阅读或修改的语法与工具操作；
3. 当前无需修改的样板结构；
4. 只有遇到对应问题才需要的高级内容。

教授第 1 类；简短说明第 2 类；只标明第 3 类的角色；暂缓第 4 类。

如果连续出现多个核心概念，优先拆成多个可见小结果，而不是一次全部讲完。

## 3. 进行显式教学

核心概念默认回答四件事：

1. 它解决什么问题；
2. 当前示例里数据怎样流动或变化；
3. 学习者运行后会看到什么；
4. 当前最可能遇到的一个误区。

可使用比喻，但必须回到真实机制。不要让比喻替代准确解释。

遇到数学内容时，先说明输入、输出和视觉含义，再介绍公式。只展开当前用到的向量或函数，不先开设完整数学预备课。

## 4. 选择示范强度

根据现有证据而不是固定等级选择：

- **完整示范**：结构陌生、多个语法同时首次出现、或缺少整体形状时，给出可运行版本并突出少数关键行。
- **局部示范**：整体结构已熟悉，只给当前机制所需的代码或步骤。
- **提示后实践**：学习者已在相邻任务中独立使用过，只提醒目标、约束或相关机制。
- **开放实践**：已展示迁移能力时，只给效果目标与边界，之后审阅其方案。

完整示范不是能力证据。示范之后优先安排一个小变化：改参数、改变方向、增加条件、替换输入，或解释一次实际现象。

## 5. 设计实践

实践应直接作用于用户当前项目或一个明确隔离的练习资产。给出：

- 要改哪里；
- 要做什么；
- 什么现象说明成功；
- 最多两个常见检查点。

不要同时给出一长串互相依赖、难以定位失败位置的操作。

用户明确排除某份旧代码、资产或做法时，新练习必须与其隔离。

## 6. 使用问题

问题只在回答能够改变下一步教学时使用：

- **预测**：改动参数后哪一部分会怎样变化？
- **因果**：为什么出现这个现象？
- **调试**：根据两个观察，先检查哪一处？
- **设计**：在两个方案之间怎样选择？

不要询问：

- 正文刚刚明说的答案；
- 未教授术语的定义；
- 对完成实践没有帮助的记忆题；
- 用户已经通过操作结果回答过的事实。

问题不是每轮必需。用户只报告结果且下一步明确时，直接反馈并继续。

## 7. 接收结果与纠错

把反馈分成三类：

- **结果符合预期**：确认具体表现，指出它证明了什么，再决定是否做邻近变化。
- **结果不同但可解释**：区分代码机制、资源设置、版本或环境因素，给最小检查顺序。
- **理解存在偏差**：先复述其判断，再明确指出错在何处，用当前现象重新解释机制。

用户报告“做了什么 + 看到了什么”时可作为实践证据。只有存在矛盾、风险较高或结论确实依赖未观察信息时，才请求额外材料。

## 8. 防止理论漂移

出现以下任一情况时停止继续铺垫，转入实践：

- 已连续解释两个以上核心概念；
- 用户开始追问“什么时候开始做”；
- 当前解释已经足以让示例运行；
- 新内容与本次可见结果没有直接关系。

可以明确说明某个细节稍后在第一次真正修改它时再讲。

## 9. 排版

让读者一眼区分“需要操作”和“用于理解”：

- 一个小节只承担一个作用；
- 列表项之间保持简短；
- 代码块前说明注意力焦点；
- 代码块后解释知识单元，不逐行翻译；
- 预期结果单独成段；
- 不用过多粗体、表格或多层编号制造视觉负担。
