# Unity / C# 项目原型库

> 用途：intake 阶段先把学员想做的东西归到下面 6 个原型之一，再据此选阶段、出任务、定验收。
> 若学员的诉求横跨多个原型，选「能在 60–90 分钟内做出最小可验证成果」的那一个作为主线，其余降级为扩展方向。
> 每个原型的「最小可验证成果」都写成**可观察表现**——能在编辑器里当场看到、且有明确的通过/不通过判据，而不是「实现了 XX 功能」这类无法验收的说法。

---

## 原型 1：2D 玩法原型

**适用起点**
- 会用 Unity Hub 建 2D 工程，能在 Hierarchy 里拖出 Sprite，能写一个挂在对象上的脚本。
- 知道 `Update` 每帧执行，但对「输入/物理/动画各自该放哪儿」没概念。
- 有想法但没做过完整循环（输入 → 反馈 → 状态变化 → 结束条件）。

**最小可验证成果（MVP 的确切可观察表现）**
1. 进入 Play 模式后，用键盘（如 A/D 或左右方向键）能把角色左右移动，松开即停；
2. 角色与场景中至少一个标记为 Trigger 的区域重叠时，Console 打印一行带该区域名字的日志，且重叠期间不重复刷屏；
3. 角色撞到实心墙壁时不会穿过去；
4. 按 R 键可把角色位置与速度恢复到初始状态。
以上 4 条同时成立即通过。任何一条说了「大概可以」即未通过。

**核心能力点**
- 区分 `Update`（逐帧逻辑、读输入）与 `FixedUpdate`（物理位移，用 `Rigidbody2D`）。
- 用 `Rigidbody2D.linearVelocity`（旧版本为 `velocity`）而不是直接改 `transform.position` 做物理移动。
- 输入读取方式统一（`Input.GetAxisRaw` 或 `InputSystem`，二选一，不混用）。
- 触发器回调 `OnTriggerEnter2D` 的触发条件与去重写法。
- 把可调数值（速度、跳跃力）暴露成 `[SerializeField]` 而不是散落在代码里的魔法数字。

**典型扩展方向**
- 加生命值/得分 UI，用 `TextMeshPro` 或 `UnityEngine.UI` 的 `Text`。
- 加一个对象池管理子弹/敌人，避免频繁 `Instantiate`/`Destroy`。
- 加简单的状态机（待机/移动/受击），用 `enum` + `switch` 起步。
- 加关卡数据配置：把每关参数存成 `ScriptableObject` 资源。
- 加音效与受击闪白，体会「反馈层次」。

**阶段切分建议（2–4 阶段）**
- 阶段 A（30 分钟）：让角色动起来。只做「键盘输入 → `Rigidbody2D` 速度 → 屏幕上看得见移动」。验收：移动方向与按键一致，松手停下。
- 阶段 B（30–45 分钟）：加碰撞与触发。验收：撞墙不穿模；进入 Trigger 区域打印一次日志。
- 阶段 C（45–90 分钟）：加重置与一个可调参数面板。验收：R 键复位；Inspector 中改速度值立刻影响手感。
- 阶段 D（可选，90 分钟以上）：加得分 UI 或对象池。

**验收要点**
- 逐条跑上面 4 条可观察表现，每条给出「通过 / 不通过 / 未验证」。
- 检查移动逻辑是否在 `FixedUpdate` 且用刚体 API；直接改 `transform.position` 视为未达标。
- 检查触发日志是否去重；重叠期间每帧刷屏视为未达标。
- 检查是否有魔法数字残留；速度值是否可在 Inspector 里调。
- 让学员口头复述「为什么移动写在 FixedUpdate」，答不出则阶段 C 之前要补。

**常见失败模式**
- **穿模**：碰撞体没配、刚体设为 `Kinematic`、或高速物体没开连续碰撞检测。
- **抖动**：在 `Update` 里改物理位置，或在 `FixedUpdate` 里读输入导致丢帧。
- **触发器不触发**：双方都没刚体；或只加了 `Collider2D` 忘了勾 `isTrigger`。
- **输入失灵**：混用新旧输入系统，或工程里 Input System Package 已启用但代码仍用旧 API。
- **一改数值就没手感**：数值是硬编码的；或改了 Inspector 里的值但运行时被代码在 `Awake` 里覆盖。
- **越写越乱**：一个脚本同时管输入、物理、UI、音效，超过 200 行后无法定位问题。

## 原型 2：3D 移动与相机

**适用起点**
- 已完成过至少一次 2D 或简单 3D 移动练习，知道 `Update`/`FixedUpdate` 的区别。
- 想做的核心是「角色在 3D 空间里移动 + 相机跟随」，而不是关卡设计。

**最小可验证成果（MVP 的确切可观察表现）**
1. 用 WASD 让角色在水平面上移动，移动方向相对于相机朝向（按 W 总是往「屏幕里」走）；
2. 角色始终贴合地面，走下坡道不会浮空或陷进去；
3. 相机在角色身后平滑跟随，转向时相机跟得上但不过冲抖动；
4. 用鼠标（或方向键）可环绕角色转动相机，相机不会穿进墙体。
以上 4 条同时成立即通过。

**核心能力点**
- 相机相对方向换算：把输入向量从相机空间转到世界空间（`Transform.TransformDirection` 或相机 forward/right 投影到水平面）。
- 3D 物理用 `Rigidbody` + `CapsuleCollider`，移动用刚体速度或 `MovePosition`。
- 相机跟随写在 `LateUpdate`，避免与角色同帧更新造成抖动。
- 相机碰撞处理（射线检测或 `Cinemachine` 的碰撞模块），理解「为什么不穿墙需要额外代码」。
- 欧拉角与 `Quaternion` 的取舍：累积旋转不要用 `transform.eulerAngles` 直接加减。

**典型扩展方向**
- 接入 `Cinemachine` 做虚拟相机、跟随与混合。
- 加冲刺/跳跃，配地面检测（`Physics.CheckSphere` 或 `Raycast`）。
- 加相机灵敏度设置并持久化到 `PlayerPrefs`。
- 加第一人称/第三人称切换。
- 用 `CharacterController` 替换刚体方案，对比两者手感差异。

**阶段切分建议（2–4 阶段）**
- 阶段 A（30 分钟）：相机相对移动。验收：按 W 永远朝屏幕里走，转相机后仍成立。
- 阶段 B（30 分钟）：相机跟随。验收：跟随写在 `LateUpdate`，快速转向时画面不抖。
- 阶段 C（30–45 分钟）：相机防穿墙。验收：贴墙转身，相机不进入墙体内部。
- 阶段 D（可选）：跳跃与地面检测。

**验收要点**
- 让学员转 90° 相机后再按 W，观察是否仍「朝屏幕里走」。
- 检查跟随代码所在回调；写在 `Update` 里要求给出不抖的理由，否则改到 `LateUpdate`。
- 检查是否用欧拉角累积旋转；若有，要求改为 `Quaternion` 相乘。
- 检查相机防穿墙是否真的用了检测；「把相机拉远一点」不算实现。

**常见失败模式**
- **相机一转就晕**：直接对 `transform.eulerAngles.x` 累加，导致角度跳变。
- **抖动**：相机跟随与角色移动在同一帧、同一回调里更新。
- **移动方向错**：用世界坐标方向而不是相机相对方向，相机转动后操作反直觉。
- **贴地失败**：用 `transform.position.y` 硬设高度而不是物理或地面检测。
- **相机穿墙**：只做了跟随没做碰撞；或用了碰撞但没设 `LayerMask`，被角色自身碰撞体挡住。

## 原型 3：编辑器工具 / 资源管线

**适用起点**
- 能写 `MonoBehaviour`，知道 `Editor` 文件夹的存在但没写过编辑器脚本。
- 面对「手动改 200 个预制体」「每次导入贴图都要改设置」这类重复劳动，想自动化。

**最小可验证成果（MVP 的确切可观察表现）**
1. 顶部菜单栏出现一个自定义菜单项（如 `Tools/我的工具`），点击后弹出一个 `EditorWindow`；
2. 窗口里有至少一个输入框或按钮；点击按钮后，对 Project 窗口中选中的资源执行一次批量修改（如统一修改贴图的 `Filter Mode`）；
3. 修改后资源的 Inspector 里数值确实变了，且 Console 打印出「处理了 N 个资源」；
4. 全程无需手动逐个点开资源。
以上 4 条同时成立即通过。

**核心能力点**
- 编辑器代码的物理隔离：脚本放在 `Editor` 文件夹或标记为 Editor 平台的 asmdef，否则打包失败。
- `[MenuItem]` 入口与 `EditorWindow` 的 `GetWindow`/`OnGUI`（或 UI Toolkit 的 `CreateGUI`）两条路线。
- `Selection.objects` / `Selection.activeObject` 读取用户当前选择。
- `AssetDatabase.SaveAssets()` / `AssetDatabase.Refresh()` 的调用时机，理解「改了内存里的资源」与「落盘」的区别。
- `Undo.RecordObject` 让操作可撤销（编辑器工具的基本礼貌）。

**典型扩展方向**
- 用 `AssetPostprocessor` 在导入时自动套用设置，取代手动跑工具。
- 改为 UI Toolkit（`VisualElement` + UXML），对比 IMGUI 的写法差异。
- 加进度条（`EditorUtility.DisplayProgressBar`），处理上千个资源时体验更好。
- 加「预览」模式：先列出将被修改的资源，用户确认后再执行。
- 把工具做成 UPM 包，供其它工程复用。

**阶段切分建议（2–4 阶段）**
- 阶段 A（30 分钟）：菜单项 + 空窗口。验收：点菜单能弹窗，Console 有日志。
- 阶段 B（30 分钟）：对选中资源做一次真实修改。验收：Inspector 数值变化可见。
- 阶段 C（30 分钟）：加撤销与落盘。验收：Ctrl+Z 能撤销；重启编辑器后修改仍在。
- 阶段 D（可选）：改成 `AssetPostprocessor` 自动触发。

**验收要点**
- 关掉编辑器重开，改动是否还在（区分「改了内存」与「已落盘」）。
- 按 Ctrl+Z 是否可撤销（`Undo.RecordObject` 是否调用）。
- 把工程切换构建目标到非 Editor 平台并触发编译，确认没有 `UnityEditor` 引用泄漏到运行时程序集。
- 检查是否硬编码资源路径；路径变了工具是否立刻失效。
- 让学员说明 `AssetDatabase.Refresh()` 不做会怎样。

**常见失败模式**
- **打包报错**：编辑器脚本没放在 `Editor` 文件夹，运行时程序集引用了 `UnityEditor` 命名空间。
- **改了没保存**：只改了内存对象没调 `AssetDatabase.SaveAssets()`，重启后白干。
- **不可撤销**：漏调 `Undo.RecordObject`，用户误操作无法回退。
- **误伤**：没做选择校验（`Selection.objects` 为空时直接遍历），抛空引用。
- **工具只对自己的工程有效**：写死了绝对路径或具体资源 GUID。

## 原型 4：数据驱动 UI 与存档

**适用起点**
- 能做出 UI 界面并让按钮点得动，但数据是散落在各脚本里的 `public` 字段。
- 目标是「把内容与代码分开」，让策划/自己改数值不用改代码。

**最小可验证成果（MVP 的确切可观察表现）**
1. 在 Project 窗口右键能创建一个配置资源（`ScriptableObject`），里面至少有 3 个可编辑字段；
2. 场景里有一个列表 UI，进入 Play 模式后按配置文件的内容生成 N 个条目（条数由配置决定，改配置不需要改代码）；
3. 点击某个条目后，UI 上显示该条目的详情；
4. 按保存键写入存档，退出 Play 模式再进入，读取后 UI 显示上次的数据；
5. 删掉存档文件后重新进入，程序不报错、回到默认状态。
以上 5 条同时成立即通过。

**核心能力点**
- `ScriptableObject` 的 `[CreateAssetMenu]` 创建入口与运行时读取方式。
- 区分「配置数据」（`ScriptableObject` 资源，只读）与「运行时存档数据」（普通 C# 类 + 序列化）。
- 序列化限制：接口、泛型字典、`null` 的 `UnityEngine.Object` 都不适合直接序列化。
- 存档路径用 `Application.persistentDataPath`，不要用工程内相对路径。
- 存档读写的健壮性：文件不存在、内容损坏、字段新增后的兼容处理。
- UI 事件订阅与解绑（`onClick.AddListener` 要配 `RemoveListener`，或改用代码绑定生命周期）。

**典型扩展方向**
- 用 JSON（`JsonUtility` 或第三方库）替代 `PlayerPrefs`，支持嵌套结构。
- 加存档版本号与迁移逻辑。
- 用 `ScriptableObject` 做事件通道，解耦 UI 与逻辑。
- 加多存档槽与删除存档。
- 把列表 UI 改为对象池复用的滚动列表，处理 200 条以上数据。

**阶段切分建议（2–4 阶段）**
- 阶段 A（30 分钟）：做出配置资源 + 读它生成 3 个 UI 条目。验收：改配置条数，UI 条数跟着变。
- 阶段 B（30 分钟）：点条目显示详情。验收：点不同条目显示不同内容。
- 阶段 C（45 分钟）：加入存档读写。验收：写入后重启仍在；删文件后能恢复默认。
- 阶段 D（可选）：加版本号与迁移。

**验收要点**
- 只改 `ScriptableObject` 资源、不改任何 `.cs`，UI 内容是否随之变化（这是本原型的核心判据）。
- 存档文件位置是否在 `Application.persistentDataPath` 下（让学员打印并指出实际路径）。
- 手动把存档文件内容改成乱码，程序是否优雅降级而不是抛异常崩掉。
- 检查 UI 事件是否有对应的解绑；反复进出 Play 模式观察监听器是否累积。
- 关闭 Domain Reload 后测试一次，确认没有依赖静态字段存活。

**常见失败模式**
- **改配置没用**：运行时又用代码覆盖了配置值，或读的是另一份硬编码默认值。
- **存档写到工程里**：用相对路径导致打包后无写权限。
- **存档一改结构就崩**：没有版本号与容错，新增字段直接反序列化失败。
- **UI 重复绑定**：每次打开面板都 `AddListener` 却不解绑，点击一次触发多次。
- **ScriptableObject 当运行时数据用**：在编辑器里改了资源，Play 模式一结束改动残留，污染源数据。
- **泛型字典存不进档**：`JsonUtility` 不支持 `Dictionary`，却不自知。

## 原型 5：小规模网络同步

**适用起点**
- 已完成至少一个单机玩法原型，了解 `Update` 与协程。
- 想验证「两个客户端能看到彼此」，目标是小规模（2–4 人、局域网或同一房间），不是商业级联机。

**最小可验证成果（MVP 的确切可观察表现）**
1. 启动第一个实例并「创建房间」，启动第二个实例并加入，两端 Console 都打印出参与者数量 2；
2. 在任一实例里移动角色，另一个实例在同一次会话中看到该角色同步移动，位置偏差肉眼不可辨；
3. 断开其中一个实例，另一个实例能收到「有人离开」的提示，且不报错、不卡死；
4. 同步逻辑与本地表现解耦：本地输入立刻响应（不走服务器往返）也能看到同步结果。
以上 4 条同时成立即通过。

**核心能力点**
- 客户端-服务器模型：谁是权威（host/authority），谁只是表现层。
- 本地输入与网络同步分离：本地先动（客户端预测的最简形式），再发状态。
- 同步频率与插值：不要在 `Update` 里每帧发网络包，用固定间隔 + 接收端插值平滑。
- 只同步必要字段：位置/朝向/状态枚举，而不是整个对象。
- 生命周期：加入/离开/重连的回调，以及对象销毁与网络对象解绑。

**典型扩展方向**
- 接入官方联网方案（如 Netcode for GameObjects 或 Mirror 一类框架），对比手写 RPC 的差异。
- 加插值/外推，让高延迟下的移动更平滑。
- 加权威服务器校验，防止客户端乱发位置。
- 同一实例多开测试自动化，减少手动开窗口的重复劳动。
- 用 `Unity Transport` 观察丢包与延迟参数对表现的影响。

**阶段切分建议（2–4 阶段）**
- 阶段 A（30–45 分钟）：两端能连上并互相看到「已连接」。验收：双实例 Console 都显示 2 人。
- 阶段 B（45 分钟）：同步位置。验收：A 动，B 看得见，且不抖。
- 阶段 C（45 分钟）：处理离开与异常断开。验收：关掉一个实例，另一个不崩且有提示。
- 阶段 D（可选）：加插值与延迟容错。

**验收要点**
- 必须双实例实测，不接受「单实例看起来正常」。
- 检查是否每帧发包；用日志统计每秒发送次数，超过每秒 30 次要求说明理由。
- 检查同步的是否为必要字段；把整个 `Transform` 或大对象序列化发出视为未达标。
- 断线测试：直接关闭进程（非优雅退出），对端是否处理。
- 让学员说明「谁说了算」；答不出权威方则阶段 C 之前要补。

**常见失败模式**
- **只有一台机器能测**：没写双实例启动方式，导致验收无法进行。
- **本地手感变差**：把本地输入改成等服务器确认再动，操作明显延迟。
- **抖动**：接收端直接 `transform.position = 收到的值`，没有插值。
- **断线崩溃**：离开回调里访问已销毁对象，抛空引用。
- **带宽失控**：每帧全字段同步，两人测试就有明显延迟。
- **网络代码与玩法代码耦合**：同步逻辑写进玩法脚本，单机模式跑不起来。

## 原型 6：性能优化专项

**适用起点**
- 已有一个能跑的原型或小工程，现在「帧率不够 / 手机发烫 / 加载很慢」。
- 会用 Profiler 打开但看不懂数据，习惯靠猜来优化。

**最小可验证成果（MVP 的确切可观察表现）**
1. 用 Profiler 采集一段固定时长的数据（如 30 秒稳定玩法），记录一个基线数值（CPU 主线程毫秒数或某方法的 GC 分配字节数）；
2. 定位到**至少一个**可量化的热点（有具体方法名 + 具体数值）；
3. 针对该热点做一处修改；
4. 用同一段场景、同样时长重新采集，给出修改前后的数字对比；
5. 重跑功能测试，确认玩法行为没有改变。
以上 5 条同时成立即通过。「感觉快了」不算通过。

**核心能力点**
- 用 Profiler 而不是猜测定位瓶颈；区分 CPU 主线程、GC、渲染、物理各模块。
- 看懂 GC Alloc 列：谁在分配，分配了多少字节，是否每帧分配。
- 区分「一次性的慢」与「每帧的慢」，优先级完全不同。
- 常见优化手段的原理与代价：缓存引用、避免装箱、复用集合、对象池、减少 `GetComponent`/`Find` 调用。
- 优化必须可回退：改前留基线、改后做对比、行为不变才算成功。

**典型扩展方向**
- 用 Profiler 的 Deep Profile 或自定义 `ProfilerMarker` 精确到方法。
- 把热点从 `Update` 迁移到事件驱动或分帧处理。
- 用 Jobs/Burst 处理大批量纯计算（注意它要求的是无托管引用的数据结构）。
- 加自动化的性能回归测试，防止优化被后续提交破坏。
- 分析内存快照，找贴图/网格的常驻占用。

**阶段切分建议（2–4 阶段）**
- 阶段 A（30 分钟）：建立基线。验收：拿出一个带时间戳的数值，能说清是怎么测的。
- 阶段 B（30–45 分钟）：定位热点。验收：能指出具体方法名与它占用的毫秒/字节。
- 阶段 C（30–45 分钟）：改一处并复测。验收：给出前后数字对比且功能未变。
- 阶段 D（可选）：建立防止回退的检查手段。

**验收要点**
- 要求「基线与复测」用完全相同的场景与时长；条件不同则结果作废。
- 检查是否只改了声称的那一处；顺手大改会污染因果判断。
- 复测必须包含功能回归——优化后行为变了等于换了个 bug。
- 让学员解释「为什么这处是瓶颈」；只会背「不要用 GetComponent」而不看数据，视为未达标。
- 记录优化的代价（可读性下降、内存上升），诚实列出。

**常见失败模式**
- **凭感觉优化**：不测就改，改完也不知道有没有用。
- **测法不可比**：基线和复测场景不同、时长不同，数字没有意义。
- **优化错对象**：花时间优化只占 2% 的代码，真正的瓶颈在渲染或物理。
- **引入新 bug**：为省分配把集合改成静态复用，结果数据在对象间串了。
- **只看编辑器数据**：编辑器开销本身就高，结论不能直接外推到真机。
- **过度优化**：把可读性牺牲在没有实测收益的地方。
