# Diagnosis：针对性诊断

来源：原文 §四；改动经审核裁定 W01（压缩题量但保留覆盖）、W03、W11（等价替代仅保留字段）。

## 原则

- 诊断围绕**用户的目标**设计，不使用与项目无关的通用考试。
- 诊断的作用是建立证据起点，不是筛选或淘汰。目的是让"待验证"尽快变成"已验证/部分验证"。
- 用户自述只作线索；诊断结论必须来自用户的实际作答或成果。

## 三类最小覆盖（不可省略）

1. 一项**理解或结果预测**；
2. 一项**问题定位**；
3. 一项**小型实现或方案设计**。

压缩交互成本的方式是**减少题量、合并呈现**（一次 1–3 题），不是跳过覆盖。缺少任一类时，能力画像中对应维度不得标"已验证"。

## 题型库

从领域包 `references/domains/<domain>/` 的 `diagnosis` 小节取题。选题目时优先选择**贴近用户当前项目**的题目；领域包题目均标注所考察维度与最小诊断类别。

**大文件不要整篇读入**：领域包题库可能很大（数百行）。先读它的索引/题号清单（通常在文件头部或末尾的"最小覆盖索引"），确定本次要用的题号，再按题号定位并只读该题正文。一次诊断只读 2–4 道题。

若某领域难以构造"小型实现"（例如纯设计类项目），改用**方案评审**替代，并在 `state.capability[].evidence` 中注明替代形式；等价替代是领域包字段，引擎不额外放宽。

## 动态难度

| 观察 | 调整 |
|---|---|
| 回答顺利 | 提高开放性、边界与变化要求 |
| 回答困难 | 缩小问题，检查前置知识 |
| 答案正确但理由不清 | 继续追问机制 |
| 会解释但不会实现 | 增加实践任务 |
| 能实现但不会排错 | 增加故障诊断与验证任务 |

## 结论标记

每项能力结论必须标为：

- **已验证**：有用户回答、成果、运行结果或测试支持；
- **部分验证**：已有证据，但覆盖不足；
- **待验证**：目前仅为自述或推测。

写入 `state.capability[]` 时：`status=已验证` 必须带 `evidence` 引用（指向 `state.evidence[].id`），且等级 ≥3；无证据时等级 ≤2 且 `status=待验证`。校验器会强制这三条。

## 收尾

- 给出简版能力画像（维度 / 等级 / 状态 / 证据 / 主要缺口 / 对当前目标的影响）。
- 明确写出"下一轮待验证的假设"——例如"假设能独立写出协程取消逻辑，将在阶段 1 任务 2 验证"。
- 请用户确认或修正；用户否定的结论降级为"待验证"，不要争论。
