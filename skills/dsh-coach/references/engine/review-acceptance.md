# Review & Acceptance：审阅与验收

来源：原文 §八；改动经审核裁定 W07（检索式复述）、W08（证据充分性定义）、W12（依据与核对状态）、W18（userOnly 核对）。

## A. 审阅

### 问题分级

- **阻塞**：导致功能、数据或核心结论错误，无法继续；
- **重要**：当前可能工作，但存在明显风险；
- **建议**：可读性、命名、简化或长期质量问题。

### 每条反馈五要素 + 两项对照

1. 位置或对应内容；
2. 发生机制；
3. 实际影响；
4. 最小修复方向；
5. 修复后的验证方式；
6. **依据**：引用的材料——**知识类结论**用问答记录（题目编号＋学员原话摘录）或文档章节；**行为类结论**用文件路径与行号、日志片段、截图位置、可复现步骤。必须具体到能核对；
7. **核对状态**：`已核对`（教练实际看过该材料）或 `推测`（未核对）。

**无法核对的判断必须降级为提问**，不得以断言形式给出。宁可少报一条，也不虚构一条"看起来很专业"的问题。

### 处理方式

优先让用户修复，不默认替用户重写全部成果。用户要求直接修时，按 `task-loop.md` 的"直接答案"路径处理并记录。

不要只询问"明白了吗"。应要求用户预测行为、处理变化、复现问题或解释为什么修复有效。

模板见 `assets/review-report.md`。

## B. 验收

> **适用范围（重要）**：本节的"充分证据"三条件**只用于阶段验收**；**单个知识结论、单题诊断不适用**——那类结论按"知识类／行为类"分层判定（见 `diagnosis.md` 的证据分层表）。本节同时被"审阅成果"指令引用（`SKILL.md` 映射表），**不得**把验收的严格度整体套到单题或单条结论上：不得因为"无法复现"就要求学生为一道概念题去跑一次实测。

### 三档结论

- **通过**：要求均有充分证据支持；
- **有条件通过**：核心成果成立，但仍有明确待修项；
- **未通过**：核心目标尚未实现或证据不足。

### "充分证据"的可操作定义

证据充分 = **可复现 + 可解释 + 可修改**（三条同时满足）：

- 可复现：别人按提交的步骤/材料能得到同一结果；
- 可解释：用户能说明机制与取舍，而不只是"跑通了"；
- 可修改：用户能按新要求改动它，并说明改动的后果。

缺任意一条 → 最高只能判"有条件通过"。核心目标未达成，或存在未清的**阻塞**项 → "未通过"。

**与单条结论的关系**：三条件针对**阶段成果**。单条结论的强度按类型判定——知识类看"无提示解释机制＋迁移"，行为类看运行结果或材料（见 `diagnosis.md`）。**单题回答正确不足以判"已验证"，但也不需要为此要求实测。**

### 验收动作（缺一不可）

1. 逐项核对阶段的 `userOnly`（用户必须亲自完成的部分），未完成不得判"通过"；
2. 逐项核对验收标准，每条给出证据引用；
3. **检索式复述**：请用户在不看资料的情况下复述本阶段的核心机制、一次关键取舍与一个失败模式，限时 5 分钟，结果写入 `retrievalRecap`；
4. AI 参与生成的成果，确认用户能解释、修改、验证后，才计入能力证据；
5. 给出结论与理由，并写明"通过后进入"或"待修项"。

### 记录

验收结果写入 `state.current`、`state.evidence[]` 与 `state.open[]`（未清的阻塞/重要项）。存在未清阻塞项时，校验器会拒绝把任务状态标为"已通过"。
