# Route：阶段路线

来源：原文 §六；改动经审核裁定 W16、W18。

## 方向

以最终成果为方向，优先建立**可验证的最小闭环**。

- 不把完整大型项目作为第一个阶段；
- 不过早引入与当前成果无关的复杂框架；
- 首阶段必须能在有限时间内产出用户可亲眼看到的结果。

## 阶段定义（字段全部必填）

| 字段 | 要求 |
|---|---|
| 可交付成果 | 可观察、可演示、可交付 |
| 本阶段非目标 | 明确不做什么，防止范围蔓延 |
| 训练能力 | 对应 `capability` 维度 |
| 必要前置知识 | 缺失则先补齐，不硬推进 |
| 具体任务 | 每个任务可在领域包时间区间内完成 |
| **用户必须亲自完成的部分** | `userOnly`，非空，验收时逐项核对 |
| 验收标准 | 可判定，与目标 `doneCriteria` 呼应 |
| 常见风险 | 来自领域包 `pitfalls` |
| 预计投入 | 时间估计 |
| 通过后进入 | 下一阶段或分支条件 |

`userOnly` 不是装饰字段：验收时必须逐项确认用户确实亲手完成，未完成的项导致结论不得为"通过"。

## 展开粒度

只详细展开**当前阶段**与**下一阶段**；更远内容保留为一行概要，避免路线僵化与上下文膨胀。

## 任务时长

单次任务时长区间取自领域包 `manifest.yml` 的 `taskMinutes`（默认 `[30, 90]`）。超过上限的任务必须拆成多个独立验收的子任务；估计值写入 `state.current.task.estimateMin`。用户可用"调整节奏"覆盖本次区间。

## 调整触发

出现下列任一情况时调整路线，并说明原因，同时写入 `state.routeChanges`：

- 项目目标发生变化；
- 用户时间或环境变化；
- 实际水平与初始判断不同；
- 用户持续卡在同一类问题；
- 用户进步速度明显快于计划；
- 实践暴露出关键前置知识缺失；
- 当前方案无法产生可验证成果；
- **阶段验收结论为"未通过"或有未清的阻塞项**。

调整只改受影响的部分，不重写整条路线；不因一次调整推翻已验证的能力结论。
