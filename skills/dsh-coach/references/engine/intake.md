# Intake：目标确认与经验收集

来源：原文 §一、§二、§三、§十四；改动经审核裁定 W13、W17、W19。

## 前提

- `assumeGoal: true`（本工作区默认）：**不追问项目目标**，用一行复述目标与可交付成果后直接进入诊断。
- `assumeGoal: false`：按下方向用户询问目标与限制。
- 无论哪种模式，`state.goal` 必须在首个任务卡之前落盘并通过校验——§二 的 6 项是后续 MVP 收敛、阶段验收与三档结论的**唯一判据来源**。

## 结构化清单（不计入"每轮 ≤3 问"配额）

一次呈现全部条目，允许用户标"未知 / 稍后"。不要逐条追问。

1. 最终想完成什么；
2. 成果以什么形式呈现（可运行 / 可交付 / 可演示）；
3. 为什么想完成它（用于判断取舍优先级）；
4. 如何判断它已经完成（**必须是可观察的判据**）；
5. 限制：时间、工具、环境、权限；
6. 当前明确不做（非目标）；
7. 已有经验（按五级自述，见下）；
8. 独立完成过的相近任务；
9. 经常卡住的环节；
10. 每周或每天可投入的时间；
11. 偏好的学习方式与反馈严格程度；
12. 可供审阅的现成材料（代码、文档、日志、截图、作品）。

## 经验自述五级（仅作线索，不作证据）

1. 只看过或听过；
2. 跟随教程完成过；
3. 能在提示下完成；
4. 能独立完成；
5. 能解释原理、排查问题并处理变化。

自述一律先记为 `状态: 待验证`，由诊断或后续证据升级。**不得**因用户自称"熟练"就直接跳过诊断。

## 目标收敛

若目标模糊（无可交付成果、无完成判据、或含两种以上解释）：

1. 提出一个**最小可验证成果**（能在一到两个任务内做出可观察结果）；
2. 说明它如何通向你描述的最终目标；
3. 请用户确认或修正后再制定路线；
4. 把被推迟的部分写入 `state.strategy.deferred`。

## 写入状态

- `goal`：statement / deliverable / why / doneCriteria / constraints / nonGoals。
- 经验与时间写进 `strategy` 与 `goal.constraints`，不写成能力等级。
- intake 结束后给出不超过 8 行的摘要，请用户纠正其中的事实错误。
