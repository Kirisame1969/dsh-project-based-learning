# 引擎修订 2（教学缺陷修复）——改动设计与审核记录

状态：**设计阶段，等待第 1 轮独立审核**。发布保持暂停（npm 与社区列表不动）。

## 0. 背景：三条真实缺陷

来自一位真实使用者的使用反馈（非推测）：

1. **只问不教**：即使明确说明"我不了解这方面的知识"，引擎也不进行详细讲解；
2. **过度严格**：明显可以通过阅读代码/文档判定的问题，仍坚持要求实测；
3. **该教的却让人自己悟**：可以直接讲授的知识，被安排成需要自行领悟的实测。

### 0.1 真实对话证据

使用者被问到的第一道题（`diagnosis-bank.md` Q1-1，生命周期顺序预测）：

> 下面脚本挂在一个初始未启用的 GameObject 上……请回答：从 `SetActive(true)` 那一刻起，Console 里按什么顺序出现这些字母、每个字母出现几次……之后又 `SetActive(false)` 会发生什么。

使用者答对之后，引擎仍要求"实测确认（实验台我已写好）"；使用者实测并说明已完成之后，引擎**再次**要求实测。

### 0.2 条款级根因（已逐条核对原文）

| 缺陷 | 责任条款 | 机制 |
|---|---|---|
| ①③ | `SKILL.md:23` R1 先做后教；`:24` R2 不得跳到第 5 级；`task-loop.md:15`「已在第 1 级时不再降级，改为缩小任务或回补前置知识」；`adapt.md:9`「概念未理解 → 回到最小示例」 | **引擎里没有"讲授"这个动作**。受阻路径的终点全是"缩任务／最小示例／回补前置"，没有一条是"把这个知识讲清楚"；"最小示例"仍要求学员自己看出来 |
| ③ | `SKILL.md` 主循环第 2 步即**诊断**（讲授只出现在第 5 步任务循环）；`intake.md:36`「自述一律先记为 `待验证`」 | 零基础学员的**第一次接触**就是测试 |
| ② | `state.md` 不变量 6（`artifact` 必须指向可核对材料）＋`review-acceptance.md:43-45`（可复现）＋`SKILL.md:25` R3（自述不是证据） | `diagnosis.md:41` 明文承认"有用户回答"即为 `已验证`，但落盘要求"材料"，而允许的材料类型全是文件行号/日志/截图/复现步骤，**没有"问答记录"**；"可复现"本是阶段验收判据，被越界用于单个知识结论 |
| ② | `SKILL.md:25` R3 措辞「用户自述只是线索」 | 立法本意是防"我熟练"这类**能力**自夸，却被无差别用于"我刚跑过一次，输出是 X"这类**操作**陈述 → 学员照做了仍不被承认 |

### 0.3 更深一层的前提错误

引擎把**一切学习**都建模为"脚手架下的自我发现"。学习至少分两类：

- **技能**（写代码、排错、设计、拆解）→ "先做后教 + 分级提示"是合适的；
- **知识**（API 名称与签名、调用顺序、语言规则、术语、文档已明的默认值）→ **适合直接讲授**，让学员自己悟是低效且有打击性的。

引擎只实现了前者，并把后者硬塞进前者。**该前提继承自原始工作流文档**，第 1–2 轮审核按"原文默认保留"原则未予质疑，因此本修订属于**对原文的实质改动**，必须重新过六项检验。

## 1. 改动清单（逐条给出精确替换）

### F1 新增"讲授"动作（R9）

**现状**：无此规则；一切学习都走脚手架。

**改为**（`SKILL.md` 常驻规则新增 R9）：

```md
- **R9 讲授（知识类不做自我发现）**：出现下列任一情形时**直接讲授**，不进入脚手架：
  1. 学员明说自己没学过、不了解该内容；
  2. 诊断或练习显示必要前置知识缺失；
  3. 内容属于**事实性知识**：API 名称与签名、调用与执行顺序、语言与类型规则、术语定义、文档已明确的默认值。
  讲授结构固定：**概念 → 为什么当前任务需要 → 最小示例 → 一道确认题**（确认题不是实测，见 R10）。
  讲授只覆盖当前目标所需范围，超出部分记入 `strategy.deferred`；讲完必须出确认题。
  **技能类内容（写代码、排错、设计、拆解）仍按 R1／R2 先做后教**，本条不适用。
```

### F2 区分两类自述（改 `intake.md:36`）

**现状**：`自述一律先记为 状态: 待验证，由诊断或后续证据升级。不得因用户自称"熟练"就直接跳过诊断。`

**改为**：

```md
自述分两类处理：
- **能力自述**（"我熟练／我会"）：先记为 `待验证`，由诊断或后续证据升级；不得仅凭自称跳过诊断。
- **缺口自述**（"我没学过 X／我不了解 Y"）：**直接采信**，立即转入 R9 讲授，不得先考一遍。
  （采信缺口自述只决定"讲不讲"，不改变后续要求：仍需确认题，技能类仍需亲手做。）
```

### F3 证据分层（改 `diagnosis.md`、`review-acceptance.md`、`state.md`）

**现状**：三态定义在 `diagnosis.md:41-43`（"有用户回答、成果、运行结果或测试支持"即可 `已验证`），但落盘要求材料；`review-acceptance.md:43-45` 的"可复现+可解释+可修改"未声明适用范围。

**改为**：

1. `review-acceptance.md` 增加**适用范围声明**：三条件**只用于阶段验收**；单个知识结论与单题诊断不适用。
2. 新增**证据分层表**（同时写进 `diagnosis.md` 与 `review-acceptance.md`）：

| 结论类型 | 判为 `已验证` 的条件 | `artifact` 可以是什么 |
|---|---|---|
| **知识类**（事实、机制、术语、顺序、规则） | 同类 2–3 题正确，或同题加难追问也正确；**单题正确只算 `部分验证`** | 问答记录（题目编号 + 学员原话摘录） |
| **行为类**（代码、功能、排错、设计取舍） | 运行结果、测试或断言支持 | 文件与行号、日志片段、截图位置、可复现步骤 |

3. `state.md` 的 `artifact` 允许类型显式加入"问答记录（题目编号＋学员原话摘录）"，并注明知识类结论可用它。

### F4 操作自述可作证据（改 `SKILL.md:25` R3）

**现状**：`- **R3 证据判定**：用户自述只是线索。每项能力标 **已验证 / 部分验证 / 待验证**；无证据不得标"已验证"。`

**改为**：

```md
- **R3 证据判定**：三类自述区别对待——
  - **能力自述**（"我熟练"）：只是线索，不得直接标"已验证"；
  - **缺口自述**（"我没学过"）：直接采信，转入 R9（见 `intake.md`）；
  - **操作自述**（"我跑了一次，输出是 X"／"我按你说的改了"）：在没有反证时按**部分验证**接受，**不得要求重复实测**；
  每项能力标 **已验证 / 部分验证 / 待验证**；无证据不得标"已验证"。
```

### F5 实测最小化（新增 R10）

```md
- **R10 实测最小化**：只有同时满足"结论依赖运行时行为"与"静态阅读代码或文档无法判定"时才要求实测。
  以下情形**不需要实测**，直接由代码或文档判定：API 名称与签名、生命周期与调用顺序、语法与类型规则、
  文档已明确的默认值、可从代码直接读出的分支逻辑。
  **每次要求实测前，必须先用一句话说明"为什么这一点无法从代码或文档判定"**；说不出理由就不得要求实测。
```

### F6 题库门槛与类型标签（改领域包）

- 每题新增两个字段：`类型`（事实性／推理性／综合）与 `前置知识`（无／基础／已学 X）；
- 规则：**事实性题不得作为首次接触题**；`前置知识` 未满足的题不得使用；
- `diagnosis-bank.md` 的 Q1-1 移入"讲授后确认题"分组，题面前补讲授要点（生命周期调用顺序与次数规则）；
- `manifest.yml` 的 `sections` 不变，字段约定写进 `domain-contract.md`。

### F7 防过度矫正（约束本次修复自身）

```md
- 讲授不得变成整章讲课：只讲当前任务所需，连续讲授不超过 2 个知识点，超出则先让学员动手；
- 讲完必须出确认题；确认题答错则**换一种表征重讲**，不是重复同一段；
- 技能类任务（写代码、排错、设计、拆解）**不得**因 R9 改为讲授；
- 讲授不得取代"学员亲手做"：写代码类成果仍须学员本人完成并运行。
```

### F8 把 F3 机械化（状态契约 1.0 → 1.1）

**动机**：本次事故的教训是"散文规则会被误用"。F3 若只写在散文里，同样会漂移。

- `evidence[]` 新增必填字段 `kind`：`知识类` | `行为类`；
- 校验器新增不变量：
  - `kind=知识类` 且 `strength=已验证` ⇒ 该结论引用的知识类证据 **≥2 条**（拦住"问一次就发已验证"）；
  - `kind=行为类` 且 `strength=已验证` ⇒ 其 `artifact` **不得**是问答记录型（必须指向运行结果/材料）；
  - `kind` 缺失或非法 ⇒ 报错；
- `schemaVersion` 升为 `1.1`；`examples/` 两个夹具、`assets/state.template.json`、`coach-selftest.mjs` 断言、`state.md` 字段表同步更新。

> 本条是本次改动中最容易被质疑为**过度设计**的一条，请在审核中重点攻击（见 §3 反方 B）。

## 3. 反方论证专章（审核者应重点攻击这两点）

**A. 「R9/R10 会把教练变回讲师，正是原始文档要防的失败模式。」**
回应：R9 的触发是**可判定的三类情形**，而非模型自选；F7 设了连续讲授上限与确认题；技能类明示不适用。若审核认为仍不足以防止"逢题就讲"，请给出更小的替代方案（例如仅在"缺口自述"时允许讲授，取消"事实性知识"这一自动触发）。

**B. 「F8 是过度设计：为一条散文规则引入 schema 变更、夹具改动与自测改动，成本高于收益。」**
回应：本次事故的根因正是"散文规则被误用"，而机械校验是唯一能在无人复核时拦住复发的手段。但请审核者判断：
- `kind` 必填是否会给正常使用带来明显摩擦？
- 「知识类 ≥2 条证据」的阈值是否合理（1 太松、3 是否过严）？
- 是否存在**更小**的机械化方案（例如只加"知识类结论不得要求实测"的 warn，而不改 schema）？
